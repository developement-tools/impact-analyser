impact-analyser

Map the routes and components of a Next.js or Nuxt app, see where every component is used, with which variants, and which pages a change can affect — before you change it.

Cartographie les routes et les composants d’une app Next.js ou Nuxt : où chaque composant est utilisé, avec quelles variantes, et quelles pages une modification peut affecter — avant de la faire.

impact-analyser reads your source code (TypeScript compiler API, Vue SFC compiler) and never runs your app. It understands what static imports cannot show on their own: layouts and wrappers, barrel files, next/dynamic, Nuxt auto-imported components and composables, nested routes, middleware and plugins.

impact-analyser lit le code source (API du compilateur TypeScript, compilateur de SFC Vue) et n’exécute jamais l’app. Il comprend ce que les imports seuls ne montrent pas : layouts et enveloppes, fichiers barrel, next/dynamic, composants et composables auto-importés de Nuxt, routes imbriquées, middleware et plugins.

Installation

Install it as a dev dependency of the Next.js or Nuxt project: it is a development tool and must not be shipped to production.

Installez-le en dépendance de développement du projet Next.js ou Nuxt : c’est un outil de développement, il ne doit pas partir en production.

npm install --save-dev impact-analyser
# pnpm add -D impact-analyser
# yarn add -D impact-analyser
# bun add -d impact-analyser

Then add the scripts you need to the package.json of the app:

Ajoutez ensuite les scripts utiles au package.json de l’app :

package.json
{
  "scripts": {
    "analyse:ui": "impact-analyser ui --open",
    "analyse:generate": "impact-analyser generate",
    "analyse:impact": "impact-analyser impact --since main"
  }
}

Requirements: Node.js 20 or later. No other setup: the framework, its version and the source folders are detected from package.json. For Nuxt 3/4, run nuxi prepare (or nuxi dev) once so that auto-imported names come from Nuxt itself — see Next.js / Nuxt.

Prérequis : Node.js 20 ou plus. Aucune autre mise en place : le framework, sa version et les dossiers sources sont détectés depuis le package.json. Pour Nuxt 3/4, lancez une fois nuxi prepare (ou nuxi dev) pour que les noms auto-importés viennent de Nuxt lui-même — voir Next.js / Nuxt.

Quick startPrise en main

From the root of the app:

Depuis la racine de l’app :

npx impact-analyser ui --open                         # visual explorer: http://127.0.0.1:4321
npx impact-analyser impact src/components/ui/Button.tsx # pages impacted by a file
npx impact-analyser impact --since main                # pages impacted by the current branch
npx impact-analyser generate                           # docs/impact-map.md for AI assistants
npx impact-analyser routes                             # every route with its layouts

Optionally, create impact-analyser.config.json to set the language, your editor or the analysis scope (see below). Everything works without it.

Facultatif : créez impact-analyser.config.json pour régler la langue, votre éditeur ou le périmètre d’analyse (voir ci-dessous). Tout fonctionne sans.

Priority and live reloadPriorité et rechargement à chaud

  • Command-line flags win over the file for one command: --lang, --include / --exclude (repeatable), --port, --out.
  • While impact-analyser ui is running, saving the config file re-runs the analysis and refreshes the browser (except port, which needs a restart). An invalid file is reported in the explorer; the previous configuration stays active until it is fixed.
  • Les options de ligne de commande priment sur le fichier, pour une commande : --lang, --include / --exclude (répétables), --port, --out.
  • Pendant que impact-analyser ui tourne, sauvegarder le fichier de config relance l’analyse et rafraîchit le navigateur (sauf port, qui demande un redémarrage). Un fichier invalide est signalé dans l’explorateur ; la configuration précédente reste active jusqu’à correction.

Analysis scopePérimètre d’analyse

include and exclude take globs relative to the app root, with .gitignore-like rules:

include et exclude prennent des globs relatifs à la racine de l’app, avec des règles proches de .gitignore :

PatternMotifMatchesCorrespond à
*everything (default of include)tout (défaut de include)
__mocks__, *.generated.tsno slash: a file or folder name at any depthsans / : un nom de fichier ou de dossier à n’importe quelle profondeur
src/legacy/**, src/legacywith a slash: anchored at the root; a folder covers its contentavec / : ancré à la racine ; un dossier couvre son contenu
*.{stories,test}.tsx, v?.ts{a,b} alternatives, ? one character, ** any number of foldersalternatives {a,b}, ? un caractère, ** n’importe quel nombre de dossiers

A file is analysed when it matches include and no exclude. An out-of-scope file is invisible: it is not a route, its imports are not followed (impact does not propagate through it) and it is not reported as dead code. The explorer shows the active scope and how many imported files were left out.

Un fichier est analysé s’il correspond à include et à aucun exclude. Un fichier hors périmètre est invisible : ce n’est pas une route, ses imports ne sont pas suivis (l’impact ne se propage pas à travers lui) et il n’est pas signalé comme code mort. L’explorateur affiche le périmètre actif et le nombre de fichiers importés laissés de côté.

Already excluded without configuration: node_modules, build folders (.next, .nuxt, .output, dist…), tests and stories (*.test.*, *.spec.*, *.stories.*) and *.d.ts files.

Déjà exclus sans configuration : node_modules, dossiers de build (.next, .nuxt, .output, dist…), tests et stories (*.test.*, *.spec.*, *.stories.*) et fichiers *.d.ts.

What is analysedCe qui est analysé

  • app/ and pages/, at the root or in src/ (like Next.js, src/ is ignored when app/ or pages/ exist at the root).
  • App Router: layout, template, error, loading, not-found, forbidden, unauthorized, global-error, global-not-found, default, route handlers, route groups (group), parallel routes @slot, private folders _folder.
  • Pages Router: _app and _document wrap every page, _error is the error page, pages/api are API routes, Next 12.0–12.1 pages/**/_middleware applies to its folder.
  • middleware.ts / proxy.ts (Next 16), at the root or in src/: applied to every route.
  • Imports: tsconfig / jsconfig paths and baseUrl, barrel files (export … from, export *), next/dynamic, React.lazy, import(), require, CSS and assets. import type is ignored (no runtime impact).
  • Components: functions, arrow functions, classes, default exports wrapped in a HOC (export default withRouter(Nav)), <Icons.Cart /> namespace usages; the "use client" directive.
  • app/ et pages/, à la racine ou dans src/ (comme Next.js, src/ est ignoré quand app/ ou pages/ existent à la racine).
  • App Router : layout, template, error, loading, not-found, forbidden, unauthorized, global-error, global-not-found, default, handlers route, groupes de routes (groupe), routes parallèles @slot, dossiers privés _dossier.
  • Pages Router : _app et _document englobent toutes les pages, _error est la page d’erreur, pages/api sont des routes API, le pages/**/_middleware de Next 12.0–12.1 s’applique à son dossier.
  • middleware.ts / proxy.ts (Next 16), à la racine ou dans src/ : appliqué à toutes les routes.
  • Imports : paths et baseUrl du tsconfig / jsconfig, fichiers barrel (export … from, export *), next/dynamic, React.lazy, import(), require, CSS et ressources. import type est ignoré (pas d’impact à l’exécution).
  • Composants : fonctions, fonctions fléchées, classes, exports par défaut enveloppés dans un HOC (export default withRouter(Nav)), usages en namespace <Icons.Cart /> ; la directive "use client".

Rendering badgesBadges de rendu

With the App Router, components are server or client ("use client"). In a Pages Router-only project, server components do not exist: components are shown as universal (rendered on the server, then hydrated).

Avec l’App Router, les composants sont serveur ou client ("use client"). Dans un projet uniquement Pages Router, les composants serveur n’existent pas : les composants sont affichés universels (rendus côté serveur puis hydratés).

Good to knowÀ savoir

  • The matcher of middleware.ts is not evaluated: the middleware is counted on every route.
  • In CI, changes to package.json, tsconfig.json, next.config.*, middleware.*, proxy.*, instrumentation.*, .env*, PostCSS and Tailwind configs are reported as global (they can affect every page).
  • “Open in app” is disabled for dynamic routes (/products/[id]): there is no concrete URL to open.
  • Le matcher de middleware.ts n’est pas évalué : le middleware est compté sur toutes les routes.
  • En CI, les modifications de package.json, tsconfig.json, next.config.*, middleware.*, proxy.*, instrumentation.*, .env*, des configs PostCSS et Tailwind sont signalées comme globales (elles peuvent affecter toutes les pages).
  • « Ouvrir dans l’app » est désactivé pour les routes dynamiques (/products/[id]) : il n’y a pas d’URL concrète à ouvrir.

La plupart des projets Nuxt 3/4 les génèrent déjà après l’installation :

What is analysedCe qui est analysé

  • Source folder: app/ in Nuxt 4, the root in Nuxt 2/3, or srcDir from nuxt.config.
  • pages/: [id], [[id]], [...slug], route groups (group), nested routes (parent.vue + parent/), Nuxt 2 _id / _; without pages/, app.vue is the only page.
  • Wrappers of each page: app.vue, the error page (error.vue, Nuxt 2 layouts/error.vue), the layout (default, or definePageMeta({ layout }) / Nuxt 2 layout option, layout: false, inherited from the parent page), route middleware (named, .global, Nuxt 2 router.middleware), plugins and global CSS.
  • Layers: layers/* (auto-registered) and local extends entries, also outside the project (../base): their pages, layouts, components, composables, middleware, plugins and server routes; the app wins when both define the same page or name. Layers from npm packages or git repositories are listed in the explorer but not analysed.
  • Nitro: server/api and server/routes (HTTP method suffixes such as [id].get.ts), server/utils auto-imports (server files only), server/middleware and server/plugins (applied to every route).
  • .vue files (HTML or Pug templates): <script> and <script setup> imports, <component :is> and resolveComponent(), components used in the template with their props (variant="x", :size, @click, v-bind, v-model), PascalCase or kebab-case tags, Options API components.
  • Auto-imports: components (folder prefixes: base/Button.vue → <BaseButton>, Lazy prefix, .client / .server), composables and utils (composables/, utils/, shared/utils), #components and #imports imports.
  • Aliases ~, @, ~~, @@, #shared, #layers/<name>.
  • Dossier source : app/ en Nuxt 4, la racine en Nuxt 2/3, ou le srcDir de nuxt.config.
  • pages/ : [id], [[id]], [...slug], groupes de routes (groupe), routes imbriquées (parent.vue + parent/), _id / _ de Nuxt 2 ; sans pages/, app.vue est la seule page.
  • Enveloppes de chaque page : app.vue, la page d’erreur (error.vue, layouts/error.vue en Nuxt 2), le layout (default, ou definePageMeta({ layout }) / option layout en Nuxt 2, layout: false, hérité de la page parente), les middleware de route (nommés, .global, router.middleware en Nuxt 2), les plugins et les CSS globales.
  • Layers : layers/* (enregistrées automatiquement) et entrées extends locales, y compris hors du projet (../base) : leurs pages, layouts, composants, composables, middleware, plugins et routes serveur ; l’app l’emporte quand les deux définissent la même page ou le même nom. Les layers issues de paquets npm ou de dépôts git sont signalées dans l’explorateur mais non analysées.
  • Nitro : server/api et server/routes (suffixes de méthode HTTP comme [id].get.ts), auto-imports de server/utils (fichiers serveur uniquement), server/middleware et server/plugins (appliqués à toutes les routes).
  • Fichiers .vue (templates HTML ou Pug) : imports de <script> et <script setup>, <component :is> et resolveComponent(), composants utilisés dans le template avec leurs props (variant="x", :size, @click, v-bind, v-model), balises en PascalCase ou kebab-case, option components de l’Options API.
  • Auto-imports : composants (préfixes de dossier : base/Button.vue → <BaseButton>, préfixe Lazy, .client / .server), composables et utils (composables/, utils/, shared/utils), imports #components et #imports.
  • Alias ~, @, ~~, @@, #shared, #layers/<nom>.

Rendering badgesBadges de rendu

Nuxt components are universal by default (rendered on the server, then hydrated); .client.vue components are client only.

Les composants Nuxt sont universels par défaut (rendus côté serveur puis hydratés) ; les composants .client.vue sont rendus uniquement côté client.

Good to knowÀ savoir

  • Not analysed: layers from npm packages or git repositories (listed in the explorer). <component :is> is resolved when its candidates are written in the code (strings, imports, resolveComponent), not when they come from data.
  • In CI, changes to nuxt.config.*, app.config.*, .nuxtrc and router.options.* are reported as global.
  • Non analysées : les layers issues de paquets npm ou de dépôts git (signalées dans l’explorateur). <component :is> est résolu quand ses candidats sont écrits dans le code (chaînes, imports, resolveComponent), pas quand ils viennent de données.
  • En CI, les modifications de nuxt.config.*, app.config.*, .nuxtrc et router.options.* sont signalées comme globales.

Map for AI assistantsCarte pour assistants IA

ContentContenu

  1. Summary: framework and version, scope, counts, dead code.
  2. High impact: components and modules reaching 50% of the pages or more.
  3. Routes: one line per route with its file, its own wrappers and the components it renders; wrappers shared by every page are written once.
  4. Layouts and wrappers with the pages they wrap.
  5. One ### <Component> block per component: file, impacted pages, props and their values (variant: "primary"×2 | "danger"×1 | unset×2), every usage as file:line with its code.
  6. Shared modules (hooks / composables, utilities, styles) and dead code.

CI / pull requestsCI / pull requests

--since <ref> analyses what a pull request contains (merge-base with the ref) and writes a Markdown summary ready to post as a comment. Changes to global files (framework config, package.json, .env*…) are flagged separately.

--since <ref> analyse le contenu d’une pull request (merge-base avec la ref) et écrit un résumé Markdown prêt à poster en commentaire. Les modifications de fichiers globaux (config du framework, package.json, .env*…) sont signalées à part.

.github/workflows/impact.yml
name: impact
on: pull_request
jobs:
  impact:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }          # history needed for --since
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx impact-analyser impact --since origin/${{ github.base_ref }} --format md > impact.md
      - run: npx impact-analyser generate --check   # optional: AI map up to date
      - run: gh pr comment ${{ github.event.number }} --body-file impact.md
        env: { GH_TOKEN: ${{ github.token }} }

SecuritySécurité

  • Nothing ships to production. impact-analyser adds nothing to your app (no plugin, middleware, component or route) and has no install script: it only runs when you call it. Installed as a dev dependency, npm ci --omit=dev does not even install it.
  • Local and read-only explorer. It listens on 127.0.0.1 only, never writes files, reads nothing outside its own folder and makes no external request.
  • DNS rebinding protection. The explorer answers only requests addressed to localhost, 127.0.0.1 or [::1] on its own port, and refuses API calls coming from another site. For a forwarded remote environment, allow its domain: "allowedHosts": ["my-codespace.app.github.dev"].
  • Security headers on the explorer: a Content-Security-Policy limited to the explorer itself, X-Frame-Options: DENY, nosniff, no referrer.
  • These rules apply to the impact-analyser server only: your app, its dev server and the APIs it calls are not affected.
  • Do not publish the output of analyze or the AI map in a public folder (public/, static/): they contain paths and excerpts of your code.
  • Rien ne part en production. impact-analyser n’ajoute rien à votre app (ni plugin, ni middleware, ni composant, ni route) et n’a aucun script d’installation : il ne s’exécute que quand vous l’appelez. Installé en dépendance de développement, npm ci --omit=dev ne l’installe même pas.
  • Explorateur local et en lecture seule. Il n’écoute que sur 127.0.0.1, n’écrit aucun fichier, ne lit rien en dehors de son propre dossier et ne fait aucun appel externe.
  • Protection contre le rebinding DNS. L’explorateur ne répond qu’aux requêtes adressées à localhost, 127.0.0.1 ou [::1] sur son propre port, et refuse les appels d’API venant d’un autre site. Pour un environnement distant redirigé, autorisez son domaine : "allowedHosts": ["mon-codespace.app.github.dev"].
  • En-têtes de sécurité sur l’explorateur : Content-Security-Policy limitée à l’explorateur lui-même, X-Frame-Options: DENY, nosniff, pas de referrer.
  • Ces règles ne concernent que le serveur d’impact-analyser : votre app, son serveur de dev et les API qu’elle appelle ne sont pas touchés.
  • Ne publiez pas la sortie d’analyze ni la carte IA dans un dossier public (public/, static/) : elles contiennent des chemins et des extraits de votre code.

Limits & troubleshootingLimites & dépannage

What static analysis cannot seeCe que l’analyse statique ne voit pas

  • Relations that only exist at runtime: imports built from strings, <component :is>, React context / Vue provide–inject, components passed as props.
  • Internal packages of a monorepo (@acme/ui) are seen as npm packages: their components are not detailed.
  • Les relations qui n’existent qu’à l’exécution : imports construits à partir de chaînes, <component :is>, context React / provide–inject Vue, composants passés en props.
  • Les packages internes d’un monorepo (@acme/ui) sont vus comme des packages npm : leurs composants ne sont pas détaillés.
